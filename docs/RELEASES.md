# Выпуск приложения и обновлений

Схема: GitHub Actions проверяет код → EAS Build собирает установочный файл с каналом `preview` или `production` → EAS Update публикует JavaScript и ресурсы в тот же канал → установленное приложение скачивает совместимое обновление. GitHub хранит исходники и запускает workflow; сами обновления доставляет Expo.

## Однократное подключение Expo

1. Создайте или выберите аккаунт Expo. На машине с исходниками выполните `npm ci`, затем `npx eas-cli@latest login` и `npx eas-cli@latest update:configure`. Команда привяжет проект и добавит в `app.json` настоящий `extra.eas.projectId` и `updates.url`. Проверьте `node scripts/check-eas-config.mjs`, затем сохраните изменения в `main`. ID проекта и URL не являются секретами; токен в файлы проекта не добавляйте.
2. Создайте персональный Expo access token на [expo.dev/settings/access-tokens](https://expo.dev/settings/access-tokens). Добавьте его в **GitHub → репозиторий → Settings → Secrets and variables → Actions** как секрет `EXPO_TOKEN`. Никогда не помещайте токен в код или чат.
3. Убедитесь, что Expo-аккаунт токена имеет право собирать приложение и публиковать обновления для привязанного проекта. При необходимости настройте среды EAS `preview` и `production` и переменные для каждой среды. В SDK 57 публикация требует `--environment`, поэтому workflow выбирает среду с тем же именем, что и канал.
4. Подготовьте учётные данные для подписания Android и iOS через EAS CLI при первом запуске сборки. Автоматическая неинтерактивная сборка в GitHub Actions сможет работать после этого. Для iOS внутренней установки также потребуется регистрация устройств и соответствующие Apple-права. Для Android профиль `preview` делает APK для внутреннего распространения.

## Первая установка

Создайте сборку в **Actions → Build installable app → Run workflow**, выбрав ветку `main`, профиль `preview` и `android`. Ссылка на результат появится в EAS Build. Установите этот APK на устройство. Для релизов через магазины выберите профиль `production`; магазины и публикация приложения требуют отдельной настройки. Только сборки, созданные после подключения EAS Update, смогут принимать такие обновления.

При локальной подготовке можно выполнить `npx eas-cli@latest build --profile preview --platform android` для первого интерактивного оформления подписи, затем использовать GitHub Actions. Канал фиксируется внутри установленной сборки: `preview` получает только `preview`, `production` — только `production`.

## Отправка обновления

1. Измените уроки, карточки или код приложения; создайте PR и дождитесь успешной проверки CI, затем объедините его с `main`.
2. В **Actions → Release OTA update → Run workflow** выберите `main`, сначала `preview`, заполните краткое описание. Проверьте обновление на установленной preview-сборке.
3. Повторите запуск для `production`, когда готовы разослать обновление установленным production-сборкам. GitHub Actions выполнит `eas update --channel ... --environment ...`. Обновление поступит при следующем запуске или возвращении в приложение при наличии интернета; после загрузки появится предложение перезапустить. Если выбрать «Позже», оно применится при следующем холодном запуске.

Публикация из другой ветки заблокирована. Одновременные публикации в один канал выполняются последовательно. Если `EXPO_TOKEN` или связь с Expo-проектом отсутствуют, workflow завершится понятной ошибкой до публикации.

## Нативные изменения

Изменение Expo SDK, нативных модулей или конфигурации сборки требует новой установочной сборки и её доставки пользователям через APK или магазин. Политика `runtimeVersion: fingerprint` отделяет несовместимые сборки от OTA-обновлений. Обычные изменения TypeScript, текста и изображений можно отправлять без переустановки, когда версии нативной среды совпадают. EAS Update не является push-уведомлением и не может разбудить закрытое приложение: доставка происходит при открытии или возвращении пользователя.
